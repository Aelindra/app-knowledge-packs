# 业务状态判读规程（State Judgment Protocol）

给消费知识包的 AI 用：仅凭一屏观察（截图 / 无障碍树 / 帧流）判定"前台应用此刻处于什么业务状态"时的标准规程。
配套角色：`README.md` 的三层聚合模式描述**包怎么造**（build-time）；本文描述**包怎么用**（runtime）。

## 规程

1. **应用识别**：由图标 / 字体 / 语言 / UI 风格 / 可见文本确定应用；同一应用的不同服、渠道、客户端变体业务规则可能不同，能确定到变体就确定到变体（对照知识包的 `variants/`）。
2. **界面定位**：将屏幕划分为状态栏 / 导航区 / 主内容区 / 浮层，判定页面类型（主页 / 详情 / 对局 / 列表 / 弹窗…）。
3. **知识对齐**：优先使用已装载的知识包（business.md 的实体、规则、词表、界面结构），把包内事实与图内可见证据逐条对齐。
   - 运行时**不建议**临时联网检索替代知识包：判读时点的在线查找慢、常不可用，且在包存在时几乎不改变结论。
   - 包缺失或不足时，可按 L1 官方源 → L2 社区源 → L3 私域笔记的顺序补充查找，但结论必须标注"未经知识包验证"。
4. **判别式下结论**：状态判定必须满足该状态的判别条件组合，缺任何一条证据即降级；**禁止凭单一锚定特征推断整体状态**（相似应用、相似模式、相似特效是常态，先验越强越容易错）。
5. **输出**：结论（状态判定）+ 依据（图内证据点 + 所引知识条目及其来源）+ 置信度（高 / 中 / 低 / `insufficient_evidence`）。对不确定处如实标注，禁止编造。

## 置信度语义

| 级别 | 含义 |
|---|---|
| 高 | 图内证据与知识包判别式全部吻合，无冲突证据 |
| 中 | 主判别条件吻合，个别辅助条件缺图内证据 |
| 低 | 仅部分吻合，存在未排除的竞争解释 |
| insufficient_evidence | 证据不足以区分候选状态，列出缺失证据清单 |

## 知识包自身的可靠性纪律

- 包内每条事实需带来源与最后核对日期；无来源内容入"待验证"小节。
- **错误的知识是负债**：判读代理可能被错的事实带偏。发现包内事实与图内证据冲突时，以图内证据为准并在结论中声明冲突。
- 图内证据与包内知识的分工：图内证据回答"现在是什么"，包内知识回答"这意味着什么"。

## 给包作者的提示（来自判读实践的通用教训）

- 知识包最值钱的部分是**判别性事实**：能把外观相近的状态区分开的机制描述（模式专属机制、状态专属的视觉语言、数值的合法范围），而不是人尽皆知的常识——模型内部已有的常识写进包里只增加 token，不增加准确度。
- 界面的"视觉语言"值得显式写：某状态下哪些控件消失 / 置灰、哪些特效出现、哪些数值范围合法。这些是判别式的原料。
